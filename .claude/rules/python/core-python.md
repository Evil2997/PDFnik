# core-python.md — правила для любого Python-файла

Загружается всегда, в каждой сессии Claude Code (лежит в
`.claude/rules/python/`, весь этот каталог подхватывается автоматически).
Применимо ко всем пяти репозиториям без исключений.

## 0. Принцип этого стандарта

Каждое правило здесь — постоянно действующий принцип, не запись о
конкретном баге. Правило не удаляется, когда конкретное нарушение
починено — оно закрывает целый класс ошибок и продолжает действовать на
весь будущий код. Если во время работы обнаруживается новая
повторяющаяся ошибка — она не чинится молча: сначала формулируется как
общее правило (новый пункт или уточнение существующего) в подходящем
файле ниже, потом чинится код. Правила не содержат `file:line` и
"сейчас в коде N случаев X" — такие ссылки протухают при первом же
рефакторинге; пример нарушения, если нужен — синтетический, не адрес в
текущем репозитории.

## 1. Типизация

- Каждая функция аннотирована полностью: все параметры и возврат,
  включая `-> None`. Внутренние `_helper`-функции не исключение —
  недоаннотированная функция выключает проверку mypy для всего, что её
  вызывает (трактуется как `Any`).
- Голых дженериков нет: `dict` → `dict[str, Any]` (или точнее),
  `asyncio.Task` → `asyncio.Task[None]`. Голый дженерик = `Any` по всем
  параметрам, типизация испаряется.
- Дефолт для `Optional`-поля — `x if x is not None else default`, не
  `x or default`. `or` допустим только когда falsy-значение заведомо
  невалидно (пустой url и подобное) и это осознанный выбор, а не
  случайность.
- `assert` не используется для валидации в проде (`python -O` вырезает
  все `assert`). Вместо него — явный `raise` или структура кода, где
  невалидное состояние в принципе недостижимо (провалидировано выше по
  стеку).
- Закрытое множество строковых значений — `StrEnum` (если пересекает
  границу сервиса/сериализуется) или `Literal` (если живёт внутри одной
  функции/модуля), никогда не голый `str`.
- `from __future__ import annotations` не добавляется: живой человек в
  этом проекте её не пишет, это маркер сгенерированного кода. На Python
  3.13 в ней нет практической необходимости — аннотации пишутся как
  обычно, без этой строки.

## 2. Именование и константы

- `snake_case` — функции/переменные/модули, `PascalCase` — классы и
  модели, `UPPER_SNAKE` — константы уровня модуля.
- Булевы имена — предикатом: `is_playlist`, `has_cache`, `can_retry`, не
  `playlist`/`cache`.
- Число или строка, которую нельзя объяснить, глядя на строку кода,
  получает имя (`_PROGRESS_PUBLISH_TIMEOUT_SEC`, не голое `5`); для
  размерных величин — суффикс единицы (`_SEC`, `_CHARS`, `_PX`).
- Сокращения, которые нужно расшифровывать — не использовать.

## 3. DRY

- **Правило трёх:** вторая копия одной и той же логики в кодовой базе —
  сигнал, третья — обязательный вынос в общий модуль/функцию.
- Любая строка/число, синхронность которого между двумя местами —
  инвариант системы, а не совпадение (имя очереди, ключ кеша, TTL, код
  ошибки, формат ключа Redis) — константа или билдер-функция в одном
  модуле, импортируется везде, никогда не собирается f-строкой на месте
  повторно.
- Одно и то же бизнес-правило, реализуемое в двух сервисах независимо
  (например, "что считать плейлистом", "что считать валидным форматом
  файла") — решение принимает ровно одна сторона и передаёт вывод через
  контракт (например, `TxtTarget.kind` выставляется ботом явно, backend
  только читает). Не выносить сам предикат в пакет контрактов —
  `.claude/rules/architecture.md` ограничивает contracts моделями и
  константами, без бизнес-логики. Два независимых и раздельно
  меняющихся определения одного правила в двух сервисах — всегда баг,
  откладывающийся на будущее.
- DRY не значит "ноль похожего кода любой ценой". Объединять стоит,
  когда изменение в одном месте **обязано** отражаться в другом. Если
  два куска кода похожи, но концептуально независимы и могут разойтись
  осознанно (например, конфигурация логгера в разных сервисах) —
  раздельные копии дешевле, чем общая зависимость, которую теперь нужно
  версионировать. Решение "объединяем / не объединяем" — осознанное, с
  комментарием на месте, а не по умолчанию в одну сторону.

## 4. CRUD-дисциплина

Применимо к любой абстракции хранения состояния — БД-репозиторий,
Redis-сессия, in-memory реестр.

- Единственная точка доступа к сущности — Repository/Port. Прямые
  запросы к хранилищу в обход него — нет, как только у сущности
  появляется второй читатель/писатель.
- Единый набор глаголов, без синонимов вперемешку в одном репозитории:
  `create` (кидает, если уже есть — не upsert), `get` (не кидает,
  возвращает `None`), `get_or_raise` (кидает доменное исключение),
  `list` (с лимитом/пагинацией, если коллекция не ограничена по
  построению), `update`, `delete`, `upsert` — отдельное явное имя, не
  перегруженный `create`.
- `create`/публикация job идемпотентны по естественному ключу, если
  вызов может продублироваться (ретрай сети, повторная доставка
  сообщения at-least-once, повторный клик пользователя). Перед тем как
  писать операцию создания — ответить на вопрос "что будет при повторном
  вызове с теми же данными".
- `delete` — явно soft или hard, решение зафиксировано в одну строку в
  докстринге метода: soft, если история нужна для отладки/метрик, hard —
  для временных/производных данных.

## 5. Dependency Injection

- Функция/класс получает зависимости (клиент БД, репозиторий, http-
  клиент, движок) параметром или через конструктор. Никогда не создаёт
  их сама внутри тела — иначе тест не может подставить фейк, а вызывающий
  код не контролирует, что реально используется.
- Никаких модульных синглтонов, которые при создании обращаются к
  внешнему ресурсу (БД, файловая система, сеть) на уровне импорта модуля.
  Конструирование — в `main()`/startup, либо лениво при первом
  использовании.
- Бизнес-логика не живёт в замыканиях, захватывающих объекты из
  DI-контейнера/фабрики. Тело обработчика — функция уровня модуля с
  зависимостями как keyword-only параметрами; сборка зависимостей и
  привязка к фреймворку (декоратор роута/подписчика) — отдельная тонкая
  функция, которая сама не содержит логики.

```python
# плохо — зависимость создаётся внутри, тест не может подменить
async def handle_job(data: dict[str, Any]) -> None:
    repo = SqliteRunRepository(RUNS_DB_PATH)
    ...

# хорошо — зависимость приходит снаружи
async def process_job(data: dict[str, Any], *, repo: RunRepository, engine: TranscribeEngine) -> None:
    ...

def register_consumer(router: RabbitRouter, *, repo: RunRepository, engine: TranscribeEngine) -> None:
    @router.subscriber("queue.name")
    async def _handle(data: dict[str, Any]) -> None:
        await process_job(data, repo=repo, engine=engine)
```

- От 4 параметров или при двух параметрах одного типа — keyword-only
  аргументы (`*,`), чтобы перестановка не ломала код молча.

## 6. Контроль потока

- Guard clause вместо вложенного `if`: ранний `return`/`continue`/`raise`
  на невалидном/граничном случае, основная логика — на верхнем уровне
  отступа, не внутри последнего `else`.

```python
# плохо
def handle(job: Job) -> Result:
    if job is not None:
        if job.is_valid():
            if not job.is_cancelled():
                return _run(job)
            else:
                raise CancelledJobError(job.id)
        else:
            raise InvalidJobError(job.id)
    else:
        raise ValueError("job is required")

# хорошо
def handle(job: Job | None) -> Result:
    if job is None:
        raise ValueError("job is required")
    if not job.is_valid():
        raise InvalidJobError(job.id)
    if job.is_cancelled():
        raise CancelledJobError(job.id)
    return _run(job)
```
Ориентир — не более 2 уровней вложенности условий в одной функции; если
нужен третий — это сигнал вынести фазу в отдельную функцию (см. п.7).

- Диспетчеризация по типу — `isinstance`/реестр `dict[type, Callable]`,
  никогда не цепочка `getattr(x, "field", None) == ...`: `getattr` с
  дефолтом маскирует отсутствие атрибута там, где оно обязано быть
  ошибкой, а не тихим переходом в `else`.

## 7. Структура функций и модулей

- Функция = одна фаза работы. Триггер для разреза — не количество строк,
  а невозможность протестировать кусок логики отдельно от остального.
  Ориентир ~50-60 строк, но линейный код без ветвлений на 80 строк лучше
  пяти функций с шестью параметрами каждая.
- Импорт модуля не выполняет I/O и не строит объекты с внешними
  зависимостями (файл, сеть, БД). Инициализация — лениво при первом
  использовании или в явном `main()`/`startup`.
- Приватные имена (`_x`) не импортируются из чужих модулей. Нужно
  снаружи — значит переименовать в публичное в модуле-владельце.
- Изменяемый объект не используется как значение параметра по умолчанию
  (`def f(items: list = [])` — запрещено; `items: list | None = None` +
  инициализация внутри).

## 8. Обработка ошибок

- `except Exception` — только на границе процесса: тело консьюмера
  очереди, HTTP-хендлер, колбэк из чужого потока/executor. Везде
  остальное — конкретные типы (`ValidationError`, `(TypeError,
  ValueError)` и т.п.).
- При перевыбросе с заменой типа/сообщения — всегда `raise ... from e`,
  иначе цепочка причин теряется в логах.
- `contextlib.suppress(Exception)` — только для действий, чей сбой не
  влияет на результат (уведомление, метрика, best-effort очистка), и
  всегда с комментарием "почему сбой тут допустим".
- Любое "сообщить о неудаче" внутри уже сработавшего `except` — само
  защищено try/suppress или вынесено в `_notify_safe`-хелпер; второй
  непойманный вызов на фоне уже случившейся аварии — частая причина
  каскадных падений.
- Наружу (клиенту/пользователю) уходит стабильный код ошибки, не
  `str(e)`: во внутренностях исключения могут быть пути, токены,
  детали инфраструктуры.
- Кастомный класс исключения заводится, как только один и тот же
  встроенный тип (`ValueError`, `RuntimeError`) используется в модуле
  для двух и более семантически разных ошибок, которые вызывающий код
  может захотеть различить программно. До этого — достаточно встроенных
  типов, иерархию не строить впрок.

## 9. Логирование

- Lazy `%`-форматирование в вызовах logger: `logger.info("x=%s", x)`, не
  `logger.info(f"x={x}")`. Число `%s` строго равно числу аргументов;
  исключение передаётся через `exc_info=` или `logger.exception(...)`,
  никогда позиционным аргументом вперемешку с обычными.
- Один формат событий на всю систему: `event=<имя> key=value key2=value2`
  — greppable, без кастомного regex на парсинг лога.
- Один способ получить логгер: `get_logger(__name__)`. Прямой
  `logging.getLogger(__name__)` в обход общей настройки — нет.
- Внутри `except` по умолчанию `logger.exception(...)` (traceback
  обязателен для аварий). `logger.error(...)` без `exc_info` — осознанное
  исключение для ожидаемых, не-аварийных случаев (невалидный входной
  payload), где сам traceback — шум.

## 10. Комментарии

- Комментарий объясняет "почему", не "что" — код и так читаем.
  Комментарий, пересказывающий следующую строку — кандидат на удаление.
- Файл не содержит шапку со своим путём (git/IDE/traceback это уже
  знают; абсолютный путь протухает при переносе репозитория).
- Код (комментарии, докстринги, идентификаторы, логи) — английский.
  User-facing строки — один язык на продукт, решается один раз на уровне
  продукта, не точечными переводами по мере обнаружения.
