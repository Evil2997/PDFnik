# testing.md — pytest и тестируемость

Загружается безусловно вместе с `core-python.md`. На него ссылается
router-таблица в шапке `core-python.md` — там сказано, при какой работе
этот файл открывать.

Читается в дополнение к `core-python.md`, когда задача касается файлов
в `tests/`, `test_*.py`, `conftest.py`, или когда обсуждается coverage.

## 1. Тестируемость закладывается в структуру, не чинится тестом постфактум

Если код нельзя протестировать без поднятия реального брокера/БД/сети —
проблема не в тесте, а в том, что бизнес-логика не отделена от
инфраструктуры (см. core-python.md, DI: зависимости параметром, не
конструирование внутри). Прежде чем писать сложный тест с моками
фреймворка — вынести тестируемую часть в функцию модуля с явными
зависимостями и протестировать её напрямую.

## 2. Внешние по отношению к домену зависимости — за интерфейсом (Protocol), в тесте — фейк, не мок фреймворка

Там, где оркестрация (порядок шагов, бизнес-решения) вызывает внешнюю
систему (whisper, ffmpeg, файловая система, сеть, брокер) — граница
описывается `Protocol`, тест подставляет простой фейк-объект,
реализующий протокол, а не патчит внутренности библиотеки через
`unittest.mock.patch`. Мок на границе библиотеки — последний вариант,
когда порт завести нельзя (сторонний SDK без асинхронной альтернативы).

## 3. `conftest.py` даёт рабочее окружение по умолчанию

Тесты запускаются без обязательной ручной подготовки env: недостающие
переменные окружения — через `os.environ.setdefault(...)` в `conftest`,
реальные значения (CI/прод) имеют приоритет и не перезаписываются.
Тяжёлые зависимости (рендеринг, ML-модели, реальные сетевые клиенты) —
стабятся на границе один раз в фикстуре, не в каждом тесте отдельно.

## 4. Имя теста описывает поведение, не реализацию

`test_create_job_raises_when_storage_key_outside_root`, не
`test_create_job_1` или `test_bug_fix`. Тест, названный по номеру бага —
через полгода не сообщает, что именно проверяет; при рефакторинге его
либо ошибочно удаляют, либо не понимают, можно ли удалить.

## 5. Совпадающие сценарии — `pytest.mark.parametrize`, не копипаста теста

Три теста, отличающихся только входным значением и ожидаемым
результатом — один параметризованный тест. Копия теста с одной
изменённой строкой — тот же DRY-инвариант из core-python.md, применённый
к тестовому коду.

## 6. `asyncio_mode = "auto"` — тест на корутину без ручного маркера

Тестовая корутина сама по себе не требует `@pytest.mark.asyncio`, если
режим настроен глобально в конфиге; не расставлять маркер вручную и не
переключать тесты на sync-обёртки вокруг `asyncio.run`.

## 7. Тест не спит реальное время дольше необходимого

Для проверки таймеров/TTL/retry-задержек — либо укороченная константа,
внедряемая через DI (см. core-python.md, п.5) на время теста, либо
`freezegun`/аналог, не `asyncio.sleep(15)` в самом тесте ради ожидания
прод-таймера.

## 8. Порог coverage — обоснованная договорённость, не самоцель

Цифра порога (`--cov-fail-under`) существует, чтобы не давать coverage
падать незаметно, а не чтобы гнаться за 100% ценой тестов, дублирующих
моки фреймворка вместо проверки поведения. Временное снижение порога —
допустимо как явное решение с причиной в PR/коммите, не тихое удаление
проверки.
