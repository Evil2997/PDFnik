## 0. OOM-петля: сервис убивается по памяти и вечно переигрывает те же задания

**Статус: произошло 2026-08-24 в 10:36. `pdf-service` остановлен вручную,
чтобы прервать петлю. Ни одного транскрипта не получено.**

Это главная находка дня. Пункт 4 (расход памяти) описывал риск - здесь он
реализовался, и вскрылся второй, более неприятный дефект: **штатный механизм
ретраев от такого падения не защищает вообще**.

### Хроника

```
10:03:19  старт декодирования первого голосового (15:44 звука)
10:20:26  добавлены ещё два задания (19:27 и 21:39)
10:21-10:23  память колеблется 8.5-9.3 ГиБ, на хосте свободно 1.8 ГиБ
10:36:53  OOM-killer убивает процесс. FinishedAt=10:36:53.152
10:36:53  docker поднимает контейнер заново (restart: unless-stopped),
          StartedAt=10:36:53.471 - через 0.3 секунды
10:36:55  RabbitMQ передоставляет ВСЕ ЧЕТЫРЕ задания, все стартуют разом
10:37:03  whisper снова декодирует с нуля, память снова растёт
~10:37    остановлено вручную: docker compose stop pdf-service
```

За 33 минуты непрерывной работы не завершилось **ни одно** задание.

### Почему это петля, а не разовый сбой

Ключевой дефект: **`attempt` не инкрементируется при OOM.**

Механизм ретраев в `txt_orders.py` живёт внутри `except Exception`:

```python
except Exception as e:
    ...
    if job.attempt < job.max_attempts:
        next_job = job.model_copy(update={"attempt": job.attempt + 1})
        await router.broker.publish(next_job.model_dump(...), queue="txt.transcribe")
        return
    await _publish_done(router, TxtDoneResult(status="error", ...))
```

OOM-killer убивает **процесс целиком** - `except` не выполняется, `ack` не
отправляется, `attempt + 1` не публикуется. RabbitMQ просто передоставляет
**исходное** сообщение с `attempt=1`. И так бесконечно:

```
OOM → рестарт → передоставка 4 заданий (attempt=1) → OOM → ...
```

`max_attempts=3` не срабатывает никогда, `txt.dead` остаётся пустой.
Подтверждено замером сразу после рестарта:

```
name             messages  messages_unacknowledged
txt.transcribe   4         4        <- те же 4, attempt не вырос
txt.dead         0         0        <- в DLQ ничего не ушло
```

Хуже того, после рестарта петля **агрессивнее исходного прогона**: все четыре
задания стартуют одновременно (`run_once transcribing` × 4 в одну секунду),
тогда как в первый раз они приходили вразнобой.

### Почему текста нет даже частично

`run_once()` пишет файл только после того, как движок вернул строку целиком:

```python
text, detected = engine.transcribe(prepared.wav_path, cfg)   # <- убито здесь
wall = time.perf_counter() - t0
out_txt.write_text(text, encoding="utf-8")                   # <- не дошло
```

А `WhisperEngine.transcribe()` материализует ленивый итератор сегментов внутри
блокировки и склеивает всё разом:

```python
text = "".join(seg.text for seg in segments).strip()
```

То есть частичного результата не существует в принципе - ни на диске, ни в
промежуточном виде. Убили на 33-й минуте - потеряно всё.

Проверено после остановки:

```
нет: 133b2913de6d4e698305450aac51ce36__3a33ba53b1.txt
нет: fb9b0e18e24842d7902b32ea29fdbbbe__2fa083eab0.txt
нет: 5f26c034f7d44fbe907e3af55a71c485__3e5c3983f1.txt
нет: d12db8255abd4c4b9a31f1bc1acd40bf__abec7816e1.txt

[TXT DONE] за всю историю обоих контейнеров: 0
vtt_done_received в боте:                    0
```

### Состояние после остановки (данные целы)

- `pdf-service`: `Status=exited`, `RestartCount=1`;
- очередь: `txt.transcribe` = 4 сообщения, все в `ready` - задания не потеряны
  и не ушли в DLQ;
- исходные `.ogg` целы на томе, все четыре;
- память хоста: было 1.8 ГиБ доступно, стало 9.4 ГиБ.

**Важно:** любой `docker compose up -d` / `make up` немедленно перезапустит
петлю - четыре задания всё ещё в очереди, конфигурация не менялась. Перед
запуском нужно либо снизить `beam_size`, либо очистить очередь:

```bash
docker exec rabbitmq rabbitmqctl purge_queue txt.transcribe
```

### Что чинить

Три отдельные вещи, по возрастанию срочности:

1. **Ресурсы под конфигурацию.** `beam_size=30` + `large-v3` на CPU не
   помещается в 15 ГиБ этой машины. Либо `beam_size=5` (дефолт faster-whisper,
   он же основной множитель памяти и времени), либо `TRANSCRIBE_MODEL=small`.
   Задаётся и через `.env`, и поштучно через `cfg` конкретного задания.
2. **Лимит памяти контейнеру.** Сейчас `Memory=0` - `pdf-service` может выбрать
   всю оперативку хоста и утащить за собой чужие процессы. С `mem_limit`
   предсказуемо падал бы только он.
3. **Ретраи, устойчивые к смерти процесса.** Текущая схема считает попытки
   только там, где успевает отработать `except`. Падение по OOM/SIGKILL её
   обходит. Нужен счётчик, переживающий процесс: заголовок `x-death` от
   RabbitMQ, TTL + DLX на очереди, либо запись попытки в `runs.db` до начала
   работы, а не после падения.

## 1. Падение всех контейнеров: `ModuleNotFoundError: pdfnik_contracts.txt_content`

**Статус: исправлено.**

### Симптом

`pdf-service` и `telegram-bot` умирали на импорте в бесконечном рестарт-цикле:

```
File "/app/main_app/rabbitmq/txt_orders.py", line 8, in <module>
    from pdfnik_contracts.txt_content import (
ModuleNotFoundError: No module named 'pdfnik_contracts.txt_content'
```

### Причина

Оба сервиса пинили пакет контрактов по тегу:

```
pdfnik-schemes @ git+https://github.com/Evil2997/PDFnik-Schemes@v1.2.1
```

Тег `v1.2.1` указывает на коммит `cc9b771` - дерево, в котором `txt_content.py`
ещё нет. Модуль добавили позже, в `78b159b` ("feat: add shared txt contracts"),
но **версию пакета в `pyproject.toml` не подняли и тег не переставили**. Docker
честно ставил то, что запинено, - пакет без нужного модуля.

Проверяется одной командой:

```bash
git -C PDFnik-Schemes ls-tree -r v1.2.1 --name-only | grep txt_content
# пусто
```

### Почему тесты этого не поймали - самое важное здесь

Это не случайность, а системный разрыв, который повторится:

- **Тесты** резолвят `pdfnik_contracts` через uv-workspace:
  `[tool.uv.sources] pdfnik-schemes = { workspace = true }` маппит пакет на
  локальную папку `PDFnik-Schemes/`. Pytest **всегда** видит самые свежие
  контракты, включая незакоммиченные правки.
- **Docker** workspace не использует вообще. В Dockerfile идёт
  `uv pip install --no-cache -r requirements.txt`, и оттуда тянется
  **запиненная git-ревизия**.

То есть зелёный прогон тестов ничего не говорит о том, соберётся ли образ.
Эти два источника разъехались, и заметил это только контейнер в проде.

### Что сделано

1. `PDFnik-Schemes`: версия 1.2.1 → 1.3.0 (новый модуль = minor), коммит
   `b5be7bd`, тег `v1.3.0`, запушено в GitHub.
2. Backend и Bot: `pyproject.toml` → `@v1.3.0`,
   `requirements.txt` → `@b5be7bd253ed2cb804576feb7a3fdacca605a267`.
3. Корневой `uv.lock` перегенерирован.

### Защита от повтора

Добавлен `tests/unit/test_schemes_contract_pin.py` - одинаковый в Backend и Bot
(намеренно дублирован: репозитории не имеют права импортировать друг друга по
`.claude/rules/architecture.md`, а пакет контрактов может содержать только
модели и константы - общему хелперу негде жить).

Тест читает **запиненную ревизию** из соседнего клона `PDFnik-Schemes` через
git (офлайн, без сети) и проверяет три инварианта:

- каждый модуль и каждое имя, которое `main_app` импортирует из
  `pdfnik_contracts`, существует в запиненной ревизии;
- `pyproject.toml` и `requirements.txt` указывают на одну и ту же ревизию;
- пин не отстаёт от версии workspace-исходников.

До фиксa тест падал ровно с тем текстом, что был в проде:

```
Failed: main_app/rabbitmq/txt_orders.py imports 'txt_content', but the pinned
pdfnik-schemes revision has no pdfnik_contracts/txt_content.py - the container
will die with ModuleNotFoundError at import
```

## 3. Лимит Telegram: бот не может скачать файл больше 20 МБ

**Статус: это ограничение платформы, не баг кода. Обойдено, сообщение исправлено.**

### Симптом

Из четырёх отправленных голосовых два транскрибировались, два ответили:

```
TelegramBadRequest: Telegram server says - Bad Request: file is too big
```

### Причина

Метод `getFile` в **облачном** Bot API отдаёт файлы размером **не более 20 МБ**.
Это документированный лимит: https://core.telegram.org/bots/api#getfile

Границу видно точно - 20 МиБ = 20 971 520 байт:

| Голосовое | Размер | Байт | Результат |
|---|---|---|---|
| 13:13 | 15.5 МБ | 16 252 928 | прошло |
| 15:44 | 18.5 МБ | 19 398 656 | прошло |
| 19:27 | 22.9 МБ | 24 012 390 | отказ |
| 21:38 | 25.5 МБ | 26 738 688 | отказ |

Никакого «попробуйте ещё раз» тут быть не может - при повторе будет тот же отказ.

### Что было багом на самом деле

Бот отвечал `"Could not download file from Telegram. Please try again."` -
совет, который отправляет пользователя по кругу.

Исправлено: перед запросом к API проверяется `file_size`, который **и так есть
в апдейте**, и ответ теперь честный - фактический размер, лимит и что делать.
Обычные сетевые сбои сохранили прежнюю формулировку про повтор.

Заодно в этом же месте:
- убран `assert file_obj is not None` из `_download_media_bytes` - `python -O`
  вырезает assert'ы (`core-python.md` п.1), заменён явным `raise`;
- повторяющаяся цепочка `msg.voice or msg.audio or msg.video or msg.document`
  сведена в один `_media_file()`.

Тесты: `PDFnik-TelegramBot/tests/unit/test_vtt_download_limit.py`, 15 штук,
включая параметризацию ровно этими четырьмя размерами.

### Как обойти лимит

**Вариант, которым воспользовались (ноль нового кода):** контракт
`TxtTranscribeJob` поддерживает `target.kind = "storage_key"` - файл берётся
прямо с общего тома `files_storage`, Telegram в этом пути не участвует вообще.

Порядок:

1. Сохранить голосовое из Telegram Desktop на диск (правая кнопка → «Сохранить как»).
2. Скопировать на том: `docker cp <файл> pdf-service:/data_files_storage/uploads/YYYY/MM/DD/<uuid>.ogg`
3. Опубликовать задание в очередь `txt.transcribe`:

```json
{
  "job_id": "<uuid4>",
  "target": {"kind": "storage_key", "value": "uploads/2026/08/24/<uuid>.ogg"},
  "reply": {"chat_id": 453083024},
  "delivery": {"source_type": "voice", "mode": "text"},
  "cfg": {}
}
```

Публикация через management API RabbitMQ:

```bash
curl -u guest:guest -H "Content-Type: application/json" \
  -X POST http://localhost:15672/api/exchanges/%2F/amq.default/publish \
  -d '{"properties":{"content_type":"application/json"},
       "routing_key":"txt.transcribe",
       "payload":"<json задания одной строкой>",
       "payload_encoding":"string"}'
```

Скрипт, который делает всё это разом, лежал в скратчпаде сессии
(`submit_voice.py`) - в репозиторий не добавлялся. При необходимости
восстанавливается по описанию выше за пять минут.

**Вариант «навсегда», который НЕ делали:** поднять собственный
`telegram-bot-api` сервер - он поднимает лимит скачивания до 2 ГБ. Требует:

- отдельный контейнер `aiogram/telegram-bot-api` в `docker-compose.yaml`;
- `api_id` / `api_hash` с https://my.telegram.org;
- общий том между API-сервером и ботом (локальный сервер возвращает путь к
  файлу на диске, а не URL);
- `AiohttpSession(api=TelegramAPIServer.from_base("http://telegram-bot-api:8081"))`
  в `bot_factory.py`;
- **разовый `logOut` в облачном API перед переездом** - иначе локальный сервер
  не примет токен. Обратный переезд требует `close` на локальном.

## 4. Транскрибация занимает ~9 ГиБ при 1.8 ГиБ свободных

**Статус: не исправлено - конфигурация ваша, менять не стали.**

### Замеры

Шесть точек за две минуты, `pdf-service`, одно активное задание:

```
10:21:33  mem=9.194GiB / 15.33GiB  cpu=354%
10:21:55  mem=9.274GiB / 15.33GiB  cpu=391%
10:22:16  mem=8.533GiB / 15.33GiB  cpu=273%
10:22:37  mem=8.657GiB / 15.33GiB  cpu=418%
10:22:58  mem=8.771GiB / 15.33GiB  cpu=517%
10:23:19  mem=8.714GiB / 15.33GiB  cpu=560%
```

Хост в этот момент: `13Gi занято, 1.2Gi свободно, 1.8Gi доступно` из 15 ГиБ.

Значение колеблется, но не растёт монотонно - **это не утечка**, а рабочий объём.

### Причина

`.env`:

```ini
TRANSCRIBE_MODEL=large-v3
TRANSCRIBE_DEVICE=cpu
TRANSCRIBE_COMPUTE_TYPE=int8
TRANSCRIBE_THREADS=8
TRANSCRIBE_WORKERS=8
TRANSCRIBE_BEAM_SIZE=30
```

`beam_size=30` держит 30 гипотез одновременно, и KV-кэш декодера large-v3
(32 слоя × 1280) умножается на это число. Отсюда основной расход.

`WhisperEngine` сериализует все транскрибации через `threading.Lock`, поэтому
очередь из четырёх заданий пик не удваивает - но один заход уже занимает почти
всю доступную память.

### Отдельно про CPU

Загрузка держалась в диапазоне **273-566% при доступных ~800%**. Железо не
насыщено. При `TRANSCRIBE_WORKERS=8` и `TRANSCRIBE_THREADS=8` восемь воркеров
делят те же восемь потоков и заметную часть времени ждут друг друга. Снижение
`WORKERS` до 1 обычно **ускоряет** - потоки достаются одному воркеру целиком.

### Риск

У контейнеров **не выставлен лимит памяти** (`docker inspect` → `Memory=0`),
то есть `pdf-service` может выбрать всю оперативку хоста. При нехватке:

1. OOM-killer убивает процесс, контейнер падает;
2. RabbitMQ передоставляет неподтверждённые задания;
3. они идут по кругу с `attempt+1`, после трёх попыток возвращают ошибку в `txt.done`.

На момент составления: `RestartCount=0`, `OOMKilled=false`, OOM ещё не срабатывал.

### Что можно сделать (не делали)

- Снизить `TRANSCRIBE_BEAM_SIZE` до 5 (дефолт faster-whisper) - основной
  множитель и памяти, и времени. На качестве распознавания сказывается слабо.
- `TRANSCRIBE_WORKERS=1` - убрать переподписку на потоки.
- Либо не трогать `.env`, а задавать `beam_size`/`workers` **поштучно** в поле
  `cfg` конкретного задания - контракт `TxtCfgOverrides` это поддерживает, и эти
  поля реально работают (в отличие от `cfg.model`, см. п.7).
- Выставить `mem_limit` контейнеру, чтобы падал предсказуемо он, а не случайный
  процесс на хосте.

### 4a. Требование владельца: даже настроенная конфигурация грузит машину слишком сильно

**Это отдельная проблема, а не следствие пункта 4. Формулировка владельца:
такая нагрузка чрезмерна.**

После правки `.env` (`beam` 30 → 15, `workers` 8 → 1, `threads` 8 → 10) OOM
ушёл, но потребление осталось высоким. Замеры на прогоне 13-минутного
голосового, large-v3, beam=15:

```
10:48  старт декодирования
       RAM контейнера: 2.1 ГиБ
10:51  3.1 ГиБ
10:55  5.1 ГиБ
10:58  5.04 ГиБ - вышло на плато, 33% всей оперативки машины
       на хосте: занято 11 ГиБ, доступно 3.7 ГиБ
```

То есть **один** транскрибируемый файл стабильно держит **треть всей памяти
машины**, а CPU - 440-460% из ~1200% доступных. Работать за компьютером
параллельно фактически нельзя, а это ноутбук, а не выделенный сервер.

Отдельно: ситуация ухудшается **с длиной записи**. Транскрипт накапливается
в оперативке целиком - `WhisperEngine.transcribe()` собирает все сегменты
разом и отдаёт строку в самом конце:

```python
text = "".join(seg.text for seg in segments).strip()
```

`run_once()` пишет на диск только после этого. Значит, на записи 21:39 расход
будет выше, чем на 13:13, и запас в 3.7 ГиБ уже не выглядит надёжным.

**Целевое требование:** транскрибация не должна занимать больше ~2-3 ГиБ и
должна оставлять машину пригодной для работы. Текущие 5+ ГиБ на файл этому
не удовлетворяют.

Что из известного бьёт прямо в это требование (подробности в разделе
«Альтернативы»):

1. **`large-v3-turbo`** - декодер 4 слоя вместо 32, KV-кэш beam-поиска падает
   кратно. Самый прямой ход, меняется одна строка в `.env`.
2. **`beam_size=5`** вместо 15 - ещё втрое меньше гипотез в памяти.
3. **`VAD=true`** - меньше материала на декодирование, значит и меньше
   накопленного транскрипта.
4. **`whisper.cpp` с квантованными GGML** - радикально ниже расход, но нужен
   новый адаптер под порт `TranscribeEngine`.
5. **Потоковая запись сегментов на диск** вместо накопления в памяти - правка
   `WhisperEngine.transcribe()`. Убирает зависимость расхода от длины записи
   и заодно даёт частичный результат при аварии (сейчас при падении теряется
   всё, см. п.0).

Пункт 5 стоит отметить особо: он чинит сразу две проблемы - и рост памяти на
длинных записях, и полную потерю работы при OOM.

## 7. `WhisperEngine` игнорирует `cfg.model`

**Статус: не исправлено, заметка оставлена в коде.**

### Как обнаружено

При сквозной проверке пайплайна опубликовал задание с `cfg: {"model": "tiny"}`.
В логах:

```
[TXT] received | run_key=file_6a554337f9f3|tiny|cpu|int8|...
Load WhisperModel | model=large-v3 | device=cpu | compute=int8 | thr=4 | wrk=1
```

`run_key` посчитан по `tiny`, а загрузилась `large-v3`.

### Причина

```python
class WhisperEngine:
    def __init__(self, model_name: str | None = None):
        self.model_name = model_name or settings.TRANSCRIBE_MODEL   # фиксируется тут

    def load(self, cfg: TranscribeConfig) -> None:
        ...
        self._model = WhisperModel(
            self.model_name,        # <- из settings, НЕ из cfg
            device=cfg.device,      # <- остальное из cfg
            compute_type=compute,
            cpu_threads=cfg.threads,
            num_workers=cfg.workers,
        )
```

Движок конструируется один раз в `register_txt_consumers()` как `WhisperEngine()`,
то есть модель берётся из `settings` навсегда. Все остальные параметры
(`device`, `compute_type`, `threads`, `workers`, `beam_size`, `patience`, `vad`,
`lang`) из `cfg` работают нормально.

При этом `make_run_key()` **хеширует `cfg.model`**:

```python
parts = [target_id, cfg.model, cfg.device, compute_type, f"thr={cfg.threads}", ...]
```

### Следствие

Два задания, отличающиеся только моделью, получают **разные ключи кеша**, но
результат обоих производит одна и та же модель. То есть кеш заполняется
дубликатами с ложной разметкой.

Сегодня безвредно: бот всегда публикует `cfg={}` и модель не переопределяет.
Станет багом, как только кто-нибудь начнёт слать `TxtCfgOverrides.model`.

### Что сделано

Только заметка в докстринге `WhisperEngine.load()` (коммит `420a41a` в Backend).
Поведение движка не менял - вне задачи «завести транскрибацию голосовых».

Починка, если понадобится: передавать `cfg.model` в `load()` и включать его в
условие `already_loaded`, чтобы модель перезагружалась при смене имени.

## Грабли: `docker compose start` не перечитывает `.env`

Правильный перезапуск после правки `.env`:

```bash
docker compose up -d --force-recreate pdf-service
```

Коварство в том, что сервис при этом выглядит совершенно здоровым и честно

## Железо, на котором всё это крутится

Прежде чем обсуждать альтернативы - вот главное ограничение, и оно не в коде:

```
CPU:  12th Gen Intel Core i7-1255U, 12 потоков (2 P-ядра + 8 E-ядер)
GPU:  Intel Iris Xe (интегрированная)
RAM:  15 ГиБ
```

Два вывода, которые определяют всё остальное:

1. **`i7-1255U` - ноутбучный 15-ваттный чип.** Из 12 потоков только 4 приходятся
   на два производительных P-ядра, остальные 8 - медленные E-ядра. Для
   ML-инференса это заметно хуже, чем «12 ядер» звучит на бумаге.
   `TRANSCRIBE_THREADS=10` раскидывает работу в основном по E-ядрам.
2. **CUDA-совместимого GPU нет.** `ctranslate2` (движок под faster-whisper)
   умеет CPU и CUDA; Intel Iris Xe не поддерживается. То есть
   `TRANSCRIBE_DEVICE=cuda` на этой машине не заработает в принципе, и вариант
   «просто включить GPU» отпадает.

Отсюда: large-v3 на этой машине - изначально тяжёлый выбор, и проблема не
столько в `beam_size`, сколько в связке «самая большая модель + слабый CPU».

## Альтернативы текущему стеку транскрибации

Раздел добавлен по запросу - обсуждались способы получить текст из тех же
голосовых. Отсортировано по отношению «выигрыш / затраты на внедрение».

**Важная оговорка про рекламу.** Про конкретный рекламный ролик ничего сказать
не могу - не видел его и не знаю, что именно рекламировали. Есть коммерческий
продукт **superwhisper**, но он, насколько мне известно, **только для macOS**,
то есть на этой Linux-машине неприменим. Если в ролике было что-то другое -
проверьте сами, я не хочу выдавать догадку за факт. Ниже - только то, что
относится к делу напрямую и что можно проверить.

### 1. `large-v3-turbo` - самый прямой выигрыш, менять почти нечего

Turbo - это large-v3 с урезанным декодером: **4 слоя вместо 32** при том же
энкодере. Практические следствия ровно по нашим двум болячкам:

- **Память.** KV-кэш декодера при beam-поиске линейно зависит от числа слоёв.
  4 вместо 32 - это примерно восьмикратное сокращение той самой величины,
  которая умножается на `beam_size` и которая нас уронила в OOM (п.0).
- **Скорость.** Декодирование - основная часть времени на длинных записях,
  и оно ускоряется в разы.
- **Язык.** Модель многоязычная, русский поддерживает. Это важное отличие от
  `distil-whisper`, где быстрые варианты в основном англоязычные и для наших
  файлов не годятся.

Внедрение: поменять одну строку в `.env`, модель скачается в `hf_cache` сама.

```ini
TRANSCRIBE_MODEL=large-v3-turbo
```

Точное имя чекпоинта под ctranslate2 стоит уточнить на HuggingFace
(варианты вида `deepdml/faster-whisper-large-v3-turbo-ct2`) - я не берусь
называть его по памяти. Качество на русском обычно чуть ниже large-v3, но
разница гораздо меньше, чем разница во времени.

### 2. Включить VAD - бесплатно на записях с паузами

Сейчас `TRANSCRIBE_VAD=false`. VAD (детектор речи) вырезает тишину до
декодирования. На живых голосовых с паузами, дыханием и обдумыванием это
убирает заметную долю материала - а платим мы именно за длительность.

```ini
TRANSCRIBE_VAD=true
```

Риск: слишком агрессивный VAD может срезать тихую речь. На важных записях
стоит сравнить результат с VAD и без на одном файле.

### 3. `beam_size` - уже уменьшен, но стоит понимать цену

`beam_size` - главный множитель и памяти, и времени. Прирост качества от него
быстро выходит на плато: разница между 5 и 15 обычно мала, между 15 и 30 -
почти незаметна, а платим линейно.

Хронология по этой машине:

| beam | workers | Память | Итог |
|---|---|---|---|
| 30 | 8 | ~9.3 ГиБ | OOM через 33 минуты, текста нет |
| 15 | 1 | ~2.1 ГиБ | запас есть, прогон идёт |

Если и с 15 будет слишком долго - следующий шаг 5 (дефолт faster-whisper),
а не смена модели.

### 4. `whisper.cpp` - если память останется проблемой

Отдельная реализация на C++ с квантованными GGML-моделями (`q5_0`, `q8_0`).
Держит large-v3 в существенно меньшем объёме памяти, чем ctranslate2, и не
тянет за собой Python-стек. Минус: это **другой движок**, то есть нужен новый
адаптер под порт `TranscribeEngine` (архитектура для этого готова - см.
`ports/transcribe_engine.py`), плюс сборка бинарника в образ.

Разумно как план Б, если turbo + VAD не хватит.

### 5. Батчевая обработка

У faster-whisper есть `BatchedInferencePipeline`, который обрабатывает
сегменты пачками и заметно ускоряет длинные записи. Требует правки
`WhisperEngine.transcribe()`. Стоит смотреть только после turbo - там выигрыш
больше при меньшей правке.

### 6. Чего делать не стоит

- **Гнаться за GPU на этой машине.** Intel Iris Xe для ctranslate2 недоступна.
- **Облачные API** (OpenAI Whisper API и аналоги) - технически снимают вопрос
  скорости совсем, но это выгрузка ваших голосовых на сторону. Решение не
  техническое, а про приватность; если записи личные или рабочие, вариант
  отпадает сам собой.
- **Увеличивать `TRANSCRIBE_THREADS` дальше.** На 12-поточном чипе с 8
  E-ядрами прирост уже нелинейный, а память растёт.

### Рекомендуемый порядок проверки

1. `large-v3-turbo` при текущем `beam=15` - замерить время и качество на одном
   файле.
2. Если качество устраивает - добавить `VAD=true`, замерить снова.
3. Если всё ещё долго - `beam_size=5`.
4. Только если и этого мало - `whisper.cpp` через новый адаптер порта.

Каждый шаг проверяется на **одном и том же** файле, иначе цифры несравнимы.
Учтите, что `make_run_key()` включает модель, beam, VAD и прочее - смена любого
параметра даёт новый ключ кеша, так что старый результат не подхватится и
замер будет честным.

## Производительность: замеры на текущем железе и оценки под GPU

Раздел собран 2026-08-24 по ходу реального прогона четырёх голосовых.

### Соглашение о RTF

Здесь и далее **RTF = wall / длительность звука**, то есть **меньше - лучше**.
RTF 3.0 означает «считалось втрое дольше, чем длится запись».

Осторожно при чтении чужих бенчмарков: половина источников использует обратную
величину и пишет «8x real-time», имея в виду RTF 0.125 в нашем смысле. Прежде
чем сравнивать - приводите к одному соглашению.

### Факт: что измерено на этой машине

`large-v3`, `int8`, `beam=15`, `workers=1`, `threads=10`, i7-1255U:

| Запись | Звук | wall | RTF | Условия |
|---|---|---|---|---|
| 13:13 | 793 с | 3233 с (54 мин) | **4.076** | параллельно шли пересборки docker-образов |
| 15:44 | 944 с | 2880 с (48 мин) | **3.049** | машина свободна |

Разница между двумя замерами - целиком посторонняя нагрузка на CPU. Вывод для
будущих измерений: **сравнивать RTF можно только на свободной машине**, иначе
цифра меряет не модель, а то, что творилось в фоне. При whisper `loadavg`
держится около 12 при 12 потоках, то есть машина занята полностью.

Практический масштаб: четыре записи общей длительностью 70 минут - это около
**3.5 часов счёта**.

### Оценки под GPU: как получены

Прямых замеров large-v3 на 50-серии найти не удалось, поэтому оценка строится
по цепочке, и каждое звено стоит перепроверить, если решение будет дорогим:

1. **Якорь снизу** - наш факт: RTF 3.049 на i7-1255U.
2. **Опубликованный замер на RTX 4090** (large-v3, float16, длинные файлы,
   последовательно): около 8x реального времени → RTF ≈ 0.13. Второй источник:
   час записи меньше чем за 9 минут → RTF ≈ 0.15.
3. **Масштабирование по вычислительной мощности:**
   RTX 5090 - 104.8 TFLOPS, RTX 5060 Ti - 23.7 TFLOPS, RTX 4090 ≈ 82.6 TFLOPS.

**Ключевая поправка, без которой оценка врёт.** Делить TFLOPS напрямую нельзя:
декодирование Whisper с beam-поиском авторегрессивно - каждый следующий токен
зависит от предыдущего. Такая нагрузка упирается не в пиковые вычисления, а в
задержки и пропускную способность памяти. Поэтому 5090 **не** даст
четырёхкратного превосходства над 5060 Ti, хотя TFLOPS различаются в 4.4 раза.
В таблице ниже заложено примерно двукратное преимущество, и диапазоны намеренно
широкие.

### Оценка

| Железо | RTF | Ускорение | Запись 21:39 | Все 4 (70 мин) |
|---|---|---|---|---|
| i7-1255U, int8 (текущее) | **3.05** | - | 66 мин | **3.5 часа** |
| RTX 5060 Ti 16 ГБ, fp16 | ~0.35-0.50 | 6-9x | ~9 мин | ~28 мин |
| RTX 5090 32 ГБ, fp16 | ~0.10-0.15 | 20-30x | ~2.6 мин | ~8-9 мин |

Батчевая обработка (`BatchedInferencePipeline`) снижает обе цифры ещё в разы:
опубликованные замеры на 4090 при `batch_size=16` дают порядка 250x реального
времени. Это отдельная правка `WhisperEngine`, не настройка.

### Точность: fp16, fp32, fp64 - частое заблуждение

Возникает соблазн рассудить «раз VRAM много, поставим точность повыше». Для
инференса это **ровно наоборот**:

- Веса Whisper обучены и распространяются в **fp16**. Считать их в fp32 или
  fp64 нечего - лишние биты не содержат информации, качество не растёт.
- **fp32 примерно вдвое медленнее fp16** на тензорных ядрах.
- **fp64 на игровых GeForce работает на 1/64 скорости fp32** - замедление
  примерно стократное. Полная пропускная способность fp64 есть только у
  серверных ускорителей, и для распознавания речи она не нужна.
- Движение в правильную сторону - **вниз**: fp16 на GPU, int8 на CPU (что у
  нас сейчас и стоит), int8 на GPU при желании.

Правило: избыток VRAM тратится на **более крупные модели и батчи**, а не на
разрядность.

### Две RTX 5090 в одной материнской плате

Вопрос: «RTF уменьшится вдвое, больше или меньше?» Ответ зависит от того, что
измерять, и это важнее самих цифр:

**Один файл - ускорения нет вообще. RTF не изменится.**
Транскрибация одной записи последовательна по своей природе: каждый токен
зависит от предыдущего, разрезать этот поток между двумя GPU нечем. Запись
21:39 как считалась ~2.6 минуты на одной 5090, так и будет считаться ~2.6
минуты на двух. Тензорный параллелизм для модели в 3 ГБ - чистые накладные
расходы, она целиком помещается в одну карту.

**Пачка файлов - масштабирование почти линейное, ~2x.**
Две карты берут по файлу каждая. Наши четыре записи вместо ~8-9 минут займут
~4-5. Ровно вдвое не выйдет: файлы разной длины, и карта, которой достались
две длинные, закончит позже. Чем больше файлов в очереди, тем ближе к
идеальным 2x.

Формулировка одной строкой: **две карты дают пропускную способность, а не
скорость отклика.** Для «получить один текст быстрее» они бесполезны, для
«разгрести очередь» - почти вдвое лучше.

Что понадобится помимо самих карт:

- **Питание.** 2 × 575 Вт только на GPU, плюс процессор и остальное - блок
  питания на 1600 Вт. В евросети (230 В, автомат 16 А = 3680 Вт) это проходит
  спокойно; в сетях на 120 В пришлось бы считать отдельно.
- **Слоты.** Платы с двумя PCIe x16 обычно делят линии как x8/x8. Для
  инференса это некритично - нагрузка упирается в вычисления, а не в шину.
- **Охлаждение и габариты.** Две карты по 575 Вт - это ~1.15 кВт тепла в
  корпусе, тут решает продувка, а не производительность.

Оговорка по существу: покупать две 5090 ради Whisper смысла нет - одна 5060 Ti
закрывает задачу с двадцатикратным запасом относительно текущего состояния.
Разбор выше имеет смысл только если карты берутся под другие задачи, а Whisper
идёт довеском.

### eGPU через Thunderbolt против настольной машины

Разница меньше, чем кажется. Инференс упирается в вычисления, а не в шину:
веса грузятся в VRAM один раз, дальше через кабель ходят крохи - аудиопризнаки
туда, текст обратно. Опубликованные замеры дают **10-20% штрафа** против
нативного PCIe, несмотря на восьмикратную разницу в пропускной способности.

Практическое ограничение важнее процентов: **5090 с её 575 Вт в
Thunderbolt-корпус поставить, скорее всего, не получится** - это вопрос питания
и габаритов, а не шины. 5060 Ti со 180 Вт - реалистичный кандидат на eGPU.
То есть выбор на практике: 5060 Ti внешне к ноутбуку либо 5090 в настольной
машине, а не «одна и та же карта двумя способами».

### Объём системной оперативки роли не играет

96 ГБ против 192 ГБ для этой задачи - **разницы никакой**. Модель живёт в VRAM,
системная память почти не участвует. Значение имеет только объём VRAM, и 16 ГБ
у 5060 Ti хватает с большим запасом: large-v3 в fp16 занимает около 3 ГБ.

Побочный, но важный эффект: с GPU проблема п.4a (5 ГиБ оперативки и
неработоспособный ноутбук во время счёта) исчезает сама - нагрузка уходит
в VRAM, системная память остаётся свободной.
